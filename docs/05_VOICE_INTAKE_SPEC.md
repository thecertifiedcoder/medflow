# MedFlow — Voice Intake Specification

## 1. Product requirement

Voice is a first-class patient intake mode alongside typing. It exists to reduce the effort required to describe a concern, not to replace patient review or a clinical interview.

## 2. Recommended implementation

Use browser `MediaRecorder` to capture a short audio clip, then upload it to a server-side transcription endpoint. Use the Google-documented `gemini-3.5-transcribe` model for prerecorded audio via the `@google/genai` SDK `ai.models.generateContent` API (passing inline audio data or Files API audio parts), subject to live runtime verification of model access, MIME compatibility and response schema once `GEMINI_API_KEY` is configured. Keep the Gemini API credential on the server only.

Use `VERBATIM` transcription mode (which is the `gemini-3.5-transcribe` API default, reinforced with explicit verbatim instructions in the server request) for patient narratives. Do not use “smart” cleanup as the default for health statements because removing disfluencies or rewriting a spoken self-correction could change meaning. The patient can edit the transcript explicitly before submitting it. This is the selected P0 approach; validate live API access and a real Android browser recording early in the sprint.

Browser `SpeechRecognition` must not be the only transcription path. MDN marks it as limited availability and notes that some browsers use server-based recognition. Typed intake remains the reliable fallback. A progressive enhancement may be considered only if it does not add complexity or send audio without clear disclosure.

## 3. Patient interaction states

1. `idle`: patient can type or start voice.
2. `requesting_permission`: browser microphone prompt is active.
3. `permission_denied` / `unsupported`: explain the issue and keep typed fallback available.
4. `recording`: show live timer and explicit “Recording” indicator.
5. `recording_stopped`: captured audio is ready; patient chooses `Transcribe`, `Record again` or `Cancel`.
6. `uploading` / `transcribing`: show progress; prevent duplicate requests.
7. `transcript_review`: display editable transcript and controls `Use this transcript`, `Re-record`, `Type instead`.
8. `empty_transcript` / `transcription_failed`: explain the issue; offer retry, re-record and manual typing.
9. `confirmed`: final text is patient-confirmed and may proceed to submission.

Never hide microphone activity. The patient must be able to cancel before uploading.

## 4. Recording constraints

- Maximum duration: 90 seconds for MVP.
- Accept only supported, explicitly validated audio MIME types generated by the browser.
- Validate content type and file size on the server; do not trust client metadata.
- Target maximum upload size: 10 MB, configurable.
- Stop recording automatically at the time limit and tell the user.
- Avoid storing recordings in Firestore or persistent object storage for the hackathon MVP.
- Process the recording in memory or short-lived request handling, then discard the audio bytes after transcription.
- Do not log raw audio, transcript contents or patient narratives to application logs.

## 5. Language handling

- Start with English/Nigerian English as the primary demonstrable path.
- Test Pidgin utterances experimentally; do not claim validated Pidgin performance.
- Use automatic language detection where supported by the selected model.
- The patient should be able to correct the transcript.
- If the transcript seems empty, nonsensical or obviously incomplete, require re-record or typed input.
- Do not translate Pidgin into English automatically unless the patient or staff can inspect the resulting transcript and the original spoken meaning is preserved. For MVP, transcript in the detected language is acceptable; AI extraction should state language/translation uncertainty.

Research caution: a 2026 Proceedings of Machine Learning Research paper reports that an off-the-shelf English model baseline had 73.7% word error rate on its Nigerian Pidgin test set, while a fine-tuned model achieved 29.6%. This is not a benchmark of Gemini 3.5 Transcribe, but it demonstrates why we must not assume generic speech recognition handles Nigerian Pidgin reliably.

## 6. Transcript integrity

Keep separate fields:
- `transcriptRaw`: transcription returned by speech model.
- `confirmedNarrative`: patient-edited/confirmed text (or typed narrative) submitted to staff; this is the canonical source text field used by the intake record.
- `inputMode`: `voice` or `typed`.
- `transcriptionModel`: model identifier, when voice was used.
- `transcriptionStatus`: `not_applicable`, `succeeded`, `failed`.
- `transcriptConfirmedAt`: timestamp, if confirmed.

Do not overwrite `transcriptRaw` when the patient edits the transcript. Save the final patient-approved text as `confirmedNarrative`. For typed intake, save the typed content directly as `confirmedNarrative` and set transcription status to `not_applicable`. The staff interface should show `confirmedNarrative` and provide access to `transcriptRaw` when useful.

## 7. Consent and disclosure

Before microphone capture, show concise plain-language disclosure that:
- the microphone is used only after the patient taps the control;
- the clip is sent to the transcription service to produce text;
- the transcript is shown for review before submission;
- the hackathon prototype uses synthetic data and must not be used to submit real patient information.

For production, privacy notices, lawful basis, consent where required, controller/processor roles, data retention, international transfer, vendor terms and a data protection impact assessment must be reviewed by qualified counsel/privacy professionals. Do not treat a demo notice as sufficient for commercial launch.

## 8. Failure behaviour

| Failure | Required behaviour |
|---|---|
| Browser lacks microphone/MediaRecorder support | Hide/disable voice with explanation; typed path available |
| Permission denied | Explain how to enable permission; typed path available |
| Recording interrupted | Preserve nothing as confirmed; offer re-record/type |
| Unsupported MIME type | Stop and show a clear compatibility message; do not upload invalid media |
| Duration/size exceeded | Stop or reject with clear limit; allow shorter retry/type |
| Transcription API unavailable | Keep the page state; offer retry or manual typing |
| Empty transcript | Do not submit empty content; re-record/type |
| Transcript contains likely recognition error | Patient must edit/confirm; staff sees voice source indicator |
| Network failure | Do not double-submit; retry with idempotency key or allow patient to resume safely |

## 9. Voice acceptance tests

- [ ] Voice control is visible and accessible on target mobile device.
- [ ] Microphone permission is requested only after explicit action.
- [ ] Recording indicator and timer work.
- [ ] Stop and cancel work.
- [ ] 90-second limit is enforced.
- [ ] Audio reaches server through protected endpoint.
- [ ] API key never appears in browser bundle/network response.
- [ ] Transcript is displayed and editable.
- [ ] Confirmed transcript is separate from raw transcript.
- [ ] A transcript cannot be submitted without user confirmation.
- [ ] Permission/API failure leaves typed intake fully usable.
- [ ] Pidgin test limitations are disclosed.
- [ ] No raw audio is persisted or logged by the application.
