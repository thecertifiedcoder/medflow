# MedFlow — Hackathon MVP Scope and Acceptance Criteria

> **Final hackathon access decision (2026-11-23):** The judge-facing experience is clinical-only. Public entry is `/demo` labelled **Judge Access**, which creates the existing Demo Clinical Staff session and opens `/staff/queue`. The normal staff-login and administrator pages are not part of the judge journey; their page routes redirect, while backend authorization boundaries remain intact. This changes the public access presentation, not the underlying clinical workflow requirements.


## 1. Product boundary

The hackathon MVP is a web application with two primary experiences:

- **Patient intake:** mobile-first, voice and typed narrative capture.
- **Clinical command dashboard:** desktop-first, real-time incoming queue and staff review.

A lightweight staff login and facility-scoped demo environment are necessary. A full hospital administration system is not.

## 2. MVP feature inventory

### P0.1 Patient entry

- Patient opens a public intake URL or QR code.
- Show a short demo/privacy notice.
- Use a minimal patient reference (generated by system); do not require unnecessary demographic fields.
- Capture only fields needed for the demo: patient display name or alias, age band/age if required for test, and narrative. Use synthetic details in demonstration.
- Patient can choose “Type my concern” or “Speak my concern”.
- Switching input modes must not discard already entered text.

**Acceptance:** patient can complete and submit typed intake on a supported mobile browser. Required fields are validated; clear errors appear; no unnecessary PII is collected.

### P0.2 Voice recording and transcript review

- Ask for microphone permission only after user presses the microphone control.
- Show visible recording state, elapsed time and stop/cancel controls.
- Capture a short recording, maximum 90 seconds in MVP.
- Send the recording to a protected server endpoint for transcription.
- Display the transcript as editable text.
- Patient must confirm the transcript before submission.
- Provide retry, re-record and typed fallback.

**Acceptance:** on the selected demo phone/browser, recording produces text; patient can edit it; confirmed text becomes the submitted narrative. If permissions, format or transcription fail, the patient can type and continue.

### P0.3 AI clinical context extraction

For both typed and confirmed voice narratives, Gemini returns structured intake information:
- concise chief concern;
- reported symptoms;
- explicit duration/onset;
- explicit severity description, if stated;
- relevant context explicitly stated by the patient;
- missing/unclear information;
- reported details to review with exact source quotes, without assigning clinical meaning;
- a concise clinician-facing summary.

Every extracted item must be grounded in the submitted narrative or marked unknown. No diagnosis, treatment or AI-assigned urgency.

**Acceptance:** valid output passes schema validation. Unsupported/invented fields are rejected or marked unknown. On invalid model response or timeout, the original patient submission remains available and shows “AI summary unavailable”.

### P0.4 Real-time staff queue

- Authenticated staff view a facility-scoped queue.
- New submissions appear without page refresh.
- Display submission time, reference, narrative source, transcript confirmation status, AI processing state, clinician-assigned priority and workflow status.
- Clicking a patient opens original narrative and structured brief side-by-side.
- Queue order: unassigned/new submissions first, then staff-assigned `Immediate review`, `Priority review`, and `Routine review`; oldest submission first within each group. This is workflow ordering, not a clinical triage protocol. Unreviewed cases must remain visible and must not be hidden because AI output is missing.

**Acceptance:** submit intake in one browser/device and see it on the staff dashboard in another without refresh. Queue state updates when staff changes status/priority.

### P0.5 Staff review and workflow priority

- Staff can mark intake as “In review”.
- Staff can set workflow priority using clearly labelled staff-assigned options: `Immediate review`, `Priority review`, `Routine review`.
- Staff can change their decision with a required reason.
- The interface must display “Assigned by clinical staff”; never “AI priority”.
- These labels are workflow values for the prototype, not validated clinical categories or promised treatment times. Each is visibly labelled as assigned by a staff member.

**Acceptance:** priority can be assigned and changed only by an authorised staff account; a reason is required for changes; the audit log records actor, timestamp, old value, new value and reason.

### P0.6 Staff confirmation and correction of AI brief

- Staff can confirm the AI-generated brief as reviewed or correct the structured brief.
- Preserve the original AI brief unchanged.
- Save staff-reviewed content separately.
- Require a correction note when staff makes a change.
- Record reviewer, timestamp and outcome in the audit trail.

**Acceptance:** confirmed/corrected state is visible; original AI draft remains accessible; corrected copy and correction note persist; an audit event is created.

### P0.7 Audit trail

Record important actions:
- patient intake created;
- transcript confirmed/edited;
- AI extraction completed/failed;
- staff opened/reviewed intake;
- workflow priority assigned/changed;
- workflow status changed.

Audit events are append-only from the application perspective. Do not expose a UI that silently edits or deletes prior audit history.

**Acceptance:** after a nurse changes priority, the detail view displays who changed it, when, from/to values and reason.

### P0.8 Failure and empty states

- Mic denied/not supported.
- Recording interrupted.
- Transcription timeout or rejected media format.
- AI extraction timeout, invalid JSON or unavailable service.
- Network interruption.
- Empty queue.
- No search/filter results.
- Session expired/unauthorised staff.

**Acceptance:** errors are understandable, retryable where safe, and never silently discard typed narrative or an already-created intake record.

### P0.9 Judge demo data

- Seed a small, clearly synthetic set of patients.
- Provide a reset path protected to demo/staff access.
- Label every generated record “DEMO DATA — fictional”.
- Keep seed data separate from real user submissions.

**Acceptance:** demo can start from a predictable queue after reset. No fake statistics are displayed as real outcomes.

## 3. P1 features (only after P0 is stable)

1. QR code containing the patient intake URL.
2. Queue filters and simple search.
3. Staff assignment.
4. Printable clinical intake brief.
5. Queue-age indicator, with clear explanation that it is elapsed time only.
6. Basic facility setup using a preconfigured demo facility.

## 4. Non-goals

- AI diagnosis, prognosis or prescription.
- Autonomous clinical urgency classification or “safe to wait” advice.
- Validated SATS/TEWS scoring.
- Real clinical deployment, patient pilots or clinical efficacy claims.
- Full medical record system.
- Billing, appointments, pharmacy, lab results or insurance.
- Complex multi-facility SaaS onboarding.
- Offline-first synchronization.
- Audio recording archive.

## 5. MVP release gate

Do not start P1 until all P0 features work together in a single end-to-end test. The release gate is the test flow in `10_TESTING_AND_DEMO_PLAN.md`.


## 6. Founder-approved Evidence Integrity Engine addition (2026-11-22)

The MVP's evidence-linked extraction requirement is strengthened by the deterministic Evidence Integrity Engine in `docs/19_EVIDENCE_INTEGRITY_ENGINE_SPEC.md`. The engine is implemented after the Milestone 2 intake/Gemini workflow is working; it is not a substitute for the original intake or staff review.

Additional acceptance criteria for the evidence-integrity milestone:

- [ ] Every evidence-bearing extracted field has a server-generated evidence state.
- [ ] A unique exact source quotation receives a server-derived UTF-16 source span.
- [ ] Missing, unmatched and repeated quotations are labelled `missing_quote`, `quote_not_found` or `ambiguous_quote`.
- [ ] The engine does not use fuzzy matching or trust model-supplied offsets/statuses.
- [ ] A provenance envelope binds the validated draft and evidence metadata to the immutable confirmed narrative using server-side hashes and HMAC-SHA-256.
- [ ] Staff can inspect source quotations and decide whether to confirm or correct the AI draft.
- [ ] The engine never creates a diagnosis, clinical score, urgency classification, treatment recommendation or workflow priority.

An exact quotation match proves only that the words can be located in the source narrative. It does not prove clinical truth or semantic correctness. See D-018 and `docs/19_EVIDENCE_INTEGRITY_ENGINE_SPEC.md`.

## 7. Phase UX-1 Platform Experience Rework acceptance criteria (2026-11-22)

Before Milestone 2 implementation begins, the application must satisfy the following Phase UX-1 information-architecture and role-separation acceptance criteria (`D-022`):

- [x] `/` functions as a clear, uncluttered entry-point selection screen with three distinct cards: **1. Patient Intake (`/intake`)**, **2. Staff Sign-In (`/staff/login`)**, and **3. Hackathon Demo Access (`/demo`)**.
- [x] `/intake` renders in the dedicated `.mf-pt` patient theme with `PatientTopBar` (`data-testid="patient-top-bar"`), zero staff/admin/demo navigation clutter, an always-visible emergency human-help banner, a 3-step patient journey structure, and an honest UX-1 Milestone 2 readiness boundary (no fake submission persistence).
- [x] `/demo` provides a dedicated judge evaluation hub explaining synthetic demonstration data (`DEMO-CLINIC-01`) with one-click **Enter as Demo Administrator** (`POST /api/demo/session/admin` → `/staff/admin`) and **Enter as Demo Clinical Staff** (`POST /api/demo/session/staff` → `/staff/queue`).
- [x] `/staff/login` is dedicated to provisioned staff Google Sign-In with role-aware post-authentication routing (`admin` → `/staff/admin`, `nurse`/`doctor` → `/staff/queue`) and a quiet link to `/demo` for judges.
- [x] `/staff/queue` provides a focused clinical workspace inside `StaffAccessGate` + `StaffWorkspaceLayout`, with real PostgreSQL queue polling, workflow/priority filters, and an intentional, educational empty state (`0` synthetic intake rows in UX-1) without embedded admin panels.
- [x] `/staff/admin` provides a dedicated facility administration workspace backed by `GET /api/staff/admin/facility` (`activeStaffCount`, `totalIntakesCount`, `unassignedIntakesCount`) for `admin` users and enforces HTTP 403 / restricted access UI (`data-testid="admin-role-restricted-panel"`) for `nurse`/`doctor` users.
- [x] `/staff/intakes/[intakeId]` renders inside `StaffAccessGate` + `StaffWorkspaceLayout`, separating all 6 clinical sections (Patient source, AI draft, Supporting evidence, Staff review, Operational workflow, Audit timeline) and handling loading, 404 not-found, and error states cleanly.
- [x] All 7 routes render without horizontal overflow across desktop (`1440×900`), tablet (`768×1024`), and mobile (`390×844`) viewports.
